# Creator Signal Intelligence — Public Beta PRD

> 版本：v0.2  
> 状态：Public Beta  
> 范围状态：Scope Frozen  
> 产品形态：本地优先的 Codex Skill + Python CLI  
> 对外名称建议：KOL List Auditor  
> 核心定位：多源达人名单审计与联系优先级决策工具

## 0. 范围冻结声明

在首轮真实用户测试前，不再增加任何 P0 功能。允许进入 P0 的变更仅限：

- 修复阻断核心链路的 Bug。
- 修复数据丢失、隐私、安全或合规问题。
- 消除影响实现或验收的文档歧义。

Public Beta 的唯一 P0 链路为：

```text
上传多份名单
→ 字段映射
→ 标准化
→ 确定性去重
→ 数据审计
→ Campaign 筛选
→ Shortlist
→ Excel 导出
→ 用户反馈回收
```

任何不直接支撑该链路的能力进入 Backlog，不得阻塞首版发布。

## 1. 产品摘要

Creator Signal Intelligence 不负责再帮用户建立一个更大的达人数据库。

它接收用户从 Nox、WaveInflu、EasyKOL、CreatiVault 或其他工具导出的达人名单，自动完成：

1. 多来源名单合并与去重。
2. 数据过期、缺失和冲突检查。
3. 不同来源的数据质量对比。
4. 根据具体 Campaign 生成可解释的联系优先级。
5. 输出可直接进入 Excel、飞书或 Airtable 的 Outreach List。
6. 回收用户审核与建联结果，为下一轮筛选提供复盘依据。

一句话价值：

> 把几份互相冲突的达人名单，变成一份知道先联系谁、为什么联系、哪些信息还需要核实的行动清单。

## 2. 目标用户

首批用户限定为：

- 海外 KOL 营销实习生或初级运营。
- 跨境品牌 Influencer Marketing 执行人员。
- 小型 KOL Agency 执行人员。
- 使用两个以上达人搜索工具，但仍依赖 Excel、飞书或 Airtable 管理名单的人。
- 手中已有真实或脱敏达人名单，能够判断分析结果是否有用的人。

不优先面向：

- 没有现成达人名单的用户。
- 需要完整 CRM、自动谈判或大规模自动发送的团队。
- 需要全网实时监控的成熟企业客户。

## 3. 用户核心问题

用户已经能通过各种数据库和 Skill 找到大量达人，但仍面临：

- 同一达人重复出现在多个来源中。
- 粉丝数、邮箱、地区和互动率互相冲突。
- 不知道数据是什么时候更新的。
- 不知道哪个工具的数据更值得信。
- 几百个候选人无法形成明确联系顺序。
- 筛选结果难以向主管或客户解释。
- 建联结果没有反向验证原来的筛选逻辑。

产品优先解决的不是“找到更多达人”，而是：

> 从现有名单中识别更值得联系的人，并降低错误数据造成的无效建联。

## 4. 核心用户任务

当用户准备一个具体 KOL Campaign 时，希望能够：

1. 上传一至五份不同来源的名单。
2. 用自然语言描述品牌、市场、受众和达人要求。
3. 查看名单中重复、过期、缺失和冲突的数据。
4. 获得一份可解释的优先联系清单。
5. 确认系统推荐是否合理。
6. 将结果导入现有工作表继续执行。
7. 在建联后回传回复结果。

## 5. Public Beta 核心范围

### P0：必须完成

#### 多源文件导入

- 支持 CSV 和 XLSX。
- 支持多文件同时导入。
- 提供 WaveInflu 和一个常用数据源的原生字段映射。
- 其他来源通过自动字段识别和人工确认完成映射。
- 未识别的原始字段不得丢失。

#### 名单审计

输出：

- 原始记录数。
- 去重后达人数。
- 不同来源重合率。
- 各来源独有达人数。
- 邮箱覆盖率。
- 关键字段缺失率。
- 过期字段比例。
- 冲突字段数量和严重程度。
- 待人工确认的疑似重复达人。

#### 确定性身份去重

自动合并只依据：

- 同平台 Platform ID 相同。
- 同平台规范化主页 URL 相同。
- 同平台规范化 Handle 相同，且不存在明确冲突。

其他跨平台或弱匹配结果只进入人工审核，不自动合并。

#### 数据质量判断

关键字段至少包括：

- Platform
- Handle
- Profile URL
- Followers
- Average Views
- Engagement Rate
- Country
- Language
- Email
- Latest Post Date
- Latest Sponsored Post Date

每个采用字段保留：

- Value
- Source
- Observed At
- Status
- Selection Reason

状态包括：

- Fresh
- Stale
- Conflict
- Missing
- Estimated
- Review Required

#### Campaign-aware Shortlist

根据 Campaign Brief 输出：

- 优先联系。
- 适合但需要补查。
- 暂不建议联系。
- 明确排除。

核心判断维度：

1. Brand Fit
2. Commercial Readiness
3. Contactability
4. Data Confidence

#### Top Creator 决策包

每位优先候选包含：

- 推荐等级和参考分数。
- 2–4 条入选理由。
- 使用的数据来源。
- 数据问题与补查建议。
- 推荐联系路径。
- 推荐采用的邮箱及来源。
- 人工审核状态。

#### 可执行导出

至少输出：

- `data_audit.xlsx`
- `creator_shortlist.xlsx`
- `merge_review.xlsx`
- `report.md`
- `feedback_template.xlsx`

文件应能直接导入飞书、Airtable 或 Google Sheets。

#### 用户反馈回收

用户可以标记：

- 合并是否正确。
- 是否认可候选。
- 联系方式是否正确。
- 是否实际联系。
- 是否送达。
- 是否回复。
- 是否为正向回复。
- 文字反馈。

系统能够重新导入反馈表并输出基础复盘。

### Backlog：不得阻塞 Public Beta 首版

以下能力不属于冻结后的 P0。只有在首轮真实用户测试完成、核心链路得到验证并重新评审优先级后，才可进入后续版本：

- Gmail 草稿。
- 飞书真实连接器。
- Live API。
- 竞品分析。
- 自动发邮件。
- 复杂内容分析。
- A/B/C 实验。
- 根据反馈自动调整评分权重。
- SaaS 前端。
- 来源质量可视化等增强型报告。

## 6. 明确不做

Public Beta 不做：

- TikTok、Instagram 或 YouTube 自建爬虫。
- 全网达人搜索。
- 全量竞品内容发现。
- Gmail 草稿。
- 飞书真实连接器。
- Live API。
- 自动发送邮件。
- 自动谈判。
- 完整 CRM。
- 复杂内容分析。
- 复杂前端 Dashboard。
- 多用户 SaaS 账号体系。
- 跨平台弱信号自动合并。
- 根据少量回复数据自动修改评分权重。
- 完整 A/B/C 分层实验系统。
- 所有第三方平台的实时 API 集成。

## 7. 核心用户流程

1. 用户安装 Skill。
2. 上传一至五份 CSV/XLSX。
3. 输入一段自然语言 Campaign Brief。
4. 系统展示自动识别的字段映射。
5. 用户确认存在歧义的列。
6. 系统执行去重、数据质量审计和初步筛选。
7. 用户处理少量疑似合并记录。
8. 系统生成最终 Shortlist 和审计报告。
9. 用户审核候选并导入现有工作表。
10. 用户完成建联后填写 Feedback Template。
11. 系统生成本轮复盘报告。

首次运行不要求用户编写 YAML、操作数据库或理解 CLI 参数。

## 8. 产品输出

### Data Audit

回答：

- 我实际有多少位不同达人？
- 哪些名单高度重复？
- 哪个来源的数据更新、更完整？
- 哪些邮箱、粉丝数和地区信息存在冲突？
- 哪些信息需要重新查询？

### Creator Shortlist

回答：

- 这次应该优先联系谁？
- 为什么？
- 使用了什么证据？
- 哪些信息仍不确定？
- 应该联系达人本人还是经纪公司？

### Feedback Report

回答：

- 用户认可了多少推荐？
- 哪些自动合并是错误的？
- 哪个来源贡献了更多被认可的候选？
- 哪个评分区间获得了更好的建联结果？
- 哪些规则需要调整？

## 9. Public Beta 成功指标

首轮目标：

- 招募 10–15 位测试用户。
- 至少 5 位完成完整运行。
- 至少 3 位将结果用于真实达人筛选。
- 至少 2 位进行第二次使用。
- 自动合并人工抽检准确率达到 95% 左右。
- 优先候选人工接受率达到 60% 左右。
- 至少收集 20 条具体错误、需求或工作流反馈。
- 至少有 3 位用户明确指出节省了哪个操作步骤。
- 至少有 1 位用户愿意主动推荐给同行。

以上为 Beta 目标，不对外宣称已经实现。

## 10. 验收标准

Public Beta 可以发布，需要满足：

1. 可导入至少两种真实来源和通用 CSV/XLSX。
2. 可处理至少 100–300 条来源记录。
3. 可正确标记重复、缺失、过期、冲突和估算状态。
4. 相同输入重复运行时结果稳定。
5. 自动合并案例经过固定测试集验证。
6. 每位优先候选都有明确理由和数据来源。
7. 输出文件可直接被电子表格软件打开。
8. 用户无需编写配置文件即可完成第一次运行。
9. 系统不能自动发送邮件或覆盖用户现有工作表。
10. 示例数据、日志和公开仓库不包含真实邮箱或公司内部数据。

## 11. 发布策略

采用陪跑式 Public Beta：

- 社交平台发布脱敏 Demo 和数据源对比案例。
- 用户提交真实或脱敏名单。
- 首次运行提供人工协助。
- 记录字段映射失败、错误合并和评分争议。
- 将重复出现的导入格式逐步沉淀为官方 Adapter。
- 五位以上用户完成真实运行后，再优化完全自助安装体验。

## 12. 核心产品主张

对外不宣传“全自动 KOL Agent”。

统一表达为：

> KOL List Auditor 可以比较不同达人搜索工具的名单，找出重复、过期和冲突数据，并根据你的 Campaign 告诉你应该优先联系谁。
